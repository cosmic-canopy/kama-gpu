# @kama/gpu — what is true in THIS repo

The two generated files carry the general rules: `AGENTS.md` is the language, and `AGENTS.package.md` is the half a
publishable library needs. `kama agents install` writes both, and a re-install rewrites them, so they are **not**
hand-edited. This file is the project-specific third, and it is the one to edit.

## What this is

**The safe WebGPU binding, a first-party package** (kama KR-25). It was decided on 2026-10-16 that it is not std: no
systems language ships one there, and `webgpu.h` still breaks between releases. wgpu handles are RAII `type resource`s,
`Copyable(bare: give)` is `AddRef`, and the surface acquire is typed and names `Occluded`. It starts at the handles a
triangle touches and grows toward the whole of `webgpu.h`. Buffers, bindings and pipelines *as released handles* are
in; *as an engine renderer* they stay out.

## Where things stand (2026-11-07, kama 0.9.874)

**Offscreen and a window work natively on Windows; the web run and the triangle's set do not exist yet.** Built:

- `src/native/webgpu.gen.kama`, the C API as kama, generated by `tools/wgpugen` from wgpu-native v29.0.1.1 (`webgpu.h`,
  `wgpu.h`) and emdawnwebgpu (Dawn v20260423.175430). The package-internal `native` module; `tools/check-bindings.sh`
  regenerates and compares it and holds every enum and flag number to both headers.
- `csrc/gpuseam.{h,c}`, the C seam: the adapter → device chain and the buffer map as polled slots, and the
  process-wide uncaptured-error and lost-device counts.
- `src/gpu.kama`, the safe API: Instance, Adapter, Device, Queue, `DeviceRequest`, Buffer with `BufferRead`, Texture,
  TextureView, CommandEncoder, RenderPass, CommandBuffer, each releasing in its destructor.
- `tests/`: an offscreen clear read back, native debug and release (pass), wasm (builds), and an xfail for an
  encoder used after `finish()`. `tools/test.sh` runs all of it.
- The surface on an `@kama/window` window: `Surface.create(instance:, window:)`, `configure`, the typed
  `acquire() -> Result<SurfaceTexture, SurfaceError>` (Occluded sleeps 32 ms natively), and `present()` as a move.
  `examples/clear` clears a real window every frame, quits on Escape and reconfigures on resize; `tools/test.sh` runs
  it for 60 frames (no skipped acquire, no WebGPU error) unless `KAMA_WINDOW_NO_DISPLAY` is set.

Next: the triangle's set (shader module, pipeline, bind group), then the web leg: a canvas surface once
`@kama/window` has its web half, and the offscreen test run in a browser with WebGPU.

**`std::app` is changing under `tests/` (2026-11-08).** kama's uncommitted KR-283 work (a binary reporting
`0.9.876+g546dd54e`) replaces `run(tick:, state:)` and `TickFn` with `run(app: Owned<App>)`, an `App` having `tick()`
and `lifecycle(event:)`. On that binary `tests/` does not compile; the bindings, the package's check, the 60-frame
window and the xfail still pass. `tests/` stays on the committed API until kama commits the change, then moves to an
`App`. The surface's lifetime follows the same lifecycle: a surface is dropped on `SurfaceLost`.

**Not published yet.** kama's floor for a first publish is `tests/` green on every target the package claims, and the
web leg has not run. kama has not ruled the amendments below, some of which change the API.

**A consumer names `@kama/window` too, for now.** `@kama/gpu` depends on it by path (`../kama-window`), and kama
allows a path dependency only in the root project or between members of one workspace, so `tests/`, the xfail and
the example each list it beside `@kama/gpu`. That ends when `@kama/window` is published and this depends on a version.

## Amendments to relay to kama's design (s8-gpu-wrapper)

What the build needed that the design does not say, for kama to rule; nothing here is decided from this repository.

1. **`instance.requestDevice(power:)`** for an offscreen device. The design names `requestDevice(surface:)`; kama has
   no optional parameters, so the surface form will be a second method (or an `Optional<Surface>` parameter).
2. **Errors are counted process-wide** (`uncapturedErrors()`, `lastErrorMessage()`, `lostDevices()`). The design
   names no channel for uncaptured errors or a lost device. A per-device one needs a state block that outlives every
   copy of the device (a copy is an `AddRef`), which the first version does not have.
3. **A device gets WebGPU's default limits**, not the adapter's, so a program that runs on one machine does not
   silently depend on its adapter.
4. **The numbers are generated and asserted, not bound by name.** The design says to take enum numbers from the
   header; the bindings carry them as `comptime` constants generated from both headers, and a `_Static_assert` per
   constant holds each to each leg's header, rather than `type extern enum` and `extern const`.
5. **The polls are `const fn`** (`DeviceRequest.poll`, `BufferRead.poll`, `Device.poll`): the slot they read is the
   seam's memory, not the kama value's, so a borrowed handle can be polled.
6. **The surface form of the request is `requestDeviceFor(surface:, power:)`,** a second method (item 1).
7. **`SurfaceError::Error` is spelled `Failed`,** since the type implements `Error`. `OutOfMemory` is kept but the
   webgpu.h both legs build against no longer reports it.
8. **`configure` takes the format** (`examples/clear` uses BGRA8Unorm). Choosing it from the surface's capabilities
   needs the adapter, which `DeviceStatus::Ready(device, queue)` does not hand over: either Ready carries the
   adapter, or the request answers the capabilities.
9. **No C reference on the window.** A `Window` is not reference-counted, so the surface must be dropped before the
   window it was made on (documented on `Surface`), rather than the seam keeping the window alive.

## Where the truth is

- **The design is kama's:** `../kama/docs/ROADMAP_DETAIL.md` § 8, at the anchor `s8-gpu-wrapper`. Read it before
  writing code. A change the build needs goes back to kama as an amendment of that section; it is not decided here.
- **kyoten builds it, as its first consumer** (ruled by kama on 2026-11-02; kyoten's KYR-52). kyoten's sessions do the
  work, and the owner relays to kama.
- **The starting code** is the WebGPU bindings the owner's games already wrote. What each assumes is in
  `../kyoten/docs/research/harvest.md` § 4 (`wgpugen`) and § 5 (the GPU device, the frame loop and capture).

## Rules

- **Never edit `../kama` from here.** A compiler or std gap goes in [KAMA_GAPS.md](KAMA_GAPS.md), with a minimal repro
  and the kama version.
- **Name no engine.** Nothing here names kyoten or a game: a tool, an editor and a game use it alike.
- **Verify, don't trust.** Compile the snippet, run it, read the emitted C. A doc is not evidence, including this one.
- **Commit on the branch, and push only when the owner asks.**
